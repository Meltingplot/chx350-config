# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

MeltingPlot CHX350 3D printer configuration repository. Contains machine configuration, calibration macros, filament profiles, and safety/automation scripts for a professional multi-axis 3D printer running Duet 3 firmware (RepRapFirmware 3.6.1).

**Language:** Duet G-code (not traditional programming — machine control scripts executed by firmware).

**No build/test/lint system.** Scripts are loaded directly by the Duet firmware at startup (`sys/config.g`) or invoked via the Duet web interface / G-code console. Validation is done manually on hardware.

## Architecture

### Boot Sequence

`sys/config.g` is the entry point — executed by firmware on startup. It:
1. Loads global variables (`sys/meltingplot/globals.g`, which ends by loading `global-override.g` if present)
2. Configures hardware (motors, heaters, fans, sensors, probes)
3. Loads CE compliance settings and machine-specific overrides
4. Restores saved parameters from non-volatile memory (`M501`)

### Machine Variants

Not every CHX350 has the same optional hardware, and the difference is expressed **as a boolean, not as G-code**: a feature is present or absent, it is never reconfigured — pin assignment is identical on every machine (CE documentation) and stays in `config.g`. Every switch is *declared with its default in `sys/meltingplot/globals.g`* — the default always describes the machine *without* the optional part, so the variable exists on every machine and consumers never need an `exists()` guard. A machine that deviates assigns the value in `sys/overrides/global-override.g`, which is loaded at the end of `globals.g` (guarded by `fileexists`). It ships fully commented out and lives in `sys/overrides/`, the directory for operator-edited files that a config update never overwrites (see "Machine-owned files"). That file may only **assign** (`set global.<name> = …`) — declaring there would fail on the second boot — and holds values only; anything requiring actual G-code (drive directions, filament monitor, heater models) belongs in `sys/overrides/machine-override`. Current switches: `has_aux_fan` (fan 2 on out2), `has_exhaust_fan` (fan 3 on out1).

Fan numbering follows the slicer convention so a slicer can never address an internal fan: **P0** = part cooling (tool-mapped via `M563 F0`), **P1** = part cooling #2 (an enable line — the fan has no PWM channel of its own and is driven by fan 0's PWM, so its mosfet must stay switched on, hence `H2 T10`), **P2** = auxiliary part cooling (OrcaSlicer `M106 P2`), **P3** = exhaust / chamber fan (OrcaSlicer air filtration), **P4+** = machine internals (radiators, water pump).

### Machine-owned files: `sys/overrides/` and `sys/generated/`

Two directories hold everything a config update must not replace, and they are told apart by who writes them. Neither the DWC config plugin (`dwc-meltingplot-config`, `PROTECTED_PATTERNS` in `dsf/config_manager.py`) nor the Pi image (`rpi-image-gen`, `layer/mp-dsf.d/protected.list`) ever overwrites a file in either; both match the whole directory, so a new machine-owned file needs no list entry anywhere. It only has to be created in the right one:

- **`sys/overrides/`** — files the **operator** edits. Shipped with the repo, fully commented out, are the three templates `global-override.g` (values only, see above), `machine-override` (G-code: drive directions, filament monitor, heater models; loaded by `config.g` and re-run by the calibration macros) and `dsf-config-override.g` (DSF and network, loaded by `dsf-config.g`). Plugin and image create a missing template from the repo and never touch an existing one. On image-based machines `printer-name.g` lives here too (written by `mp-dsf-seed` / `mp-set-printer-name`, editable in DWC, loaded last by `dsf-config.g` so it wins over any `M550`; gitignored), and so does `spool-catalog.csv`, the machine's spool catalog (written by macro `edit-spool-catalog`, editable in DWC, not shipped, gitignored; see "Material data and filament consumption").
- **`sys/generated/`** — files the **machine** writes about itself, never to be edited by hand: `nozzle<tool>.g`, `nozzle-type<tool>.g`, `filament-diameter<tool>.g`, `spool<tool>.g`, `bed-surface.g`, `last-filament-temp.g`, `filament-profiles.csv` (the profiles created on the machine, `filament-profile/store-index.g`), the scanning Z-probe calibration `szp-{standard,touch}-mode-{warm,cold}.g` (macro `calibration/z-height`) and `szp-touch-z-offset.g` (macros `z-probe/offset/*`). Nothing ships there and the whole directory is gitignored; DSF creates it on the first `echo >` (parent directories are created on every file write, verified in `KeywordHandler.cs` / `LinkService.cs`). Every reader guards with `fileexists`.

Files whose location RRF fixes stay where they are and keep their explicit entries in both lists: `sys/config-override.g` (M500) and the per-profile `filaments/<name>/{config-override,temps,material,nozzle-*}.g`. The deploy pipeline must not number or CRC anything in the two directories (`tools/gcode_crc.py -x 'sys/overrides/*' -x 'sys/generated/*'`); an edit would break the line's CRC. `sys/meltingplot/migrate.g` moves the pre-3.7 files out of `sys/meltingplot/` and `sys/meltingplot/z-probe/` on boot (called by `dsf-config.g` and `globals.g`, idempotent; an old file wins over a freshly shipped template; `M471` does not create the target directory, so it runs `M470` for `sys/generated/` first), deletes the pre-3.7 names of the files the 3.7 renaming replaced (see "Naming") and can be removed once every machine runs 3.7.

### Print Flow

`start.g` → `print/prepare.g` (called by the slicer start G-code: door checks → homing → bed leveling → nozzle clean → prime) → print → `stop.g` → `print/finish.g` (cleanup, safety reset)

### Naming

- **Files** are kebab-case and end in `.g`, like RRF's own `filament-error.g` or `driver-stall.g`. The operator macros in `macros/` carry no extension, because DWC lists them by file name. **Globals** are snake_case (an RRF identifier cannot contain a hyphen), never camelCase.
- **A folder is a subsystem**, and where the subsystem owns globals the folder name is their prefix: `spool/` ↔ `spool_*`, `filament/` ↔ `filament_*`. Inside a folder a file is named for what it does, not after the folder again (`spool/store.g`, not `spool/store-spool.g`); it is always called by its full path.
- **A verb has one meaning:** `load`/`unload` means moving filament and nothing else (a parameter file is *applied*, a CSV is *read*); `on-<file>` = called by that profile file, not by the firmware; `confirm-` = operator dropdown with the configured value preselected, cancel keeps it; `store-` = write globals to `sys/generated/`; `create-` = ask for and write a missing file; `apply-` = run a parameter file; `find-` = resolve a path; `wait-` = block until a condition holds.
- **A global is named for what it holds**, not for how it is used: `z_motor_stalled[]` (flags, not a count), `z_motor_stall_deadline` (an `upTime`, not a duration), `motion_axis_delta[]` (a distance, not a bool). A profile file hands values over in globals named after the file (`material.g` → `material_*`); per-tool state is never named like a transfer value (`spool_net_weight[tool]` versus the list `material_spool_weights`).
- **No basename twice:** a `sys/` helper and an operator macro never share a name.
- **Names that must not change** without a migration: a global whose name is written into a file on the machine — `nozzle_diameter` (`sys/generated/nozzle<tool>.g`), `last_filament_temp`, `szp_touch_z_offset`, `filament_temp_*` (every `temps.g`), `filament_max_flow_rate` (`nozzle-<key>.g`), `deferred_filament_load_t0` (`load.g` before 2026-07) — and every global an operator may assign in `global-override.g` (`has_*`, `idle_heater_*`, `z_motor_stall_time_max`, `szp_*`, `preheat_bed_temp`, `debug`). Renaming one breaks the boot of a machine whose file still uses the old name. The same holds for a path that a generated profile file or the slicer calls, see below.

### Flows in the CHX 350 UI

An operator macro can carry comments that the CHX 350 operator UI (DWC plugin `CHX350`, `src/plugins/CHX350/flows/`) shows as a guided flow: a tile on a page, a step list, and every prompt as a full-page step with text, live values and touch inputs. The firmware skips comments, so the macro runs unchanged in classic DWC and on PanelDue, where the same prompts appear as plain message boxes. A changed flow needs a config deploy only, never a web deploy. Flows so far: `calibration/z-height`, `calibration/heightmap`, `calibration/align-z-axis`, `maintenance/prepare-bed`.

- **Front matter** (turns the macro into a flow with a tile): YAML between two `; ---` lines at the very top of the file, every line a comment (Jekyll style). Keys: `title` (required), `description`, `icon` (mdi name), `page` (`start`, `calibrate`, `service`; none = no tile), `order`, `enabled` (Jinja that renders `true` when the tile may start; without it the tile starts only while the machine is idle), `hint` (shown instead of the description while the tile is disabled). Quote a value that starts with `{`.
- **Steps:** `;;` lines directly above an M291 are that prompt's Markdown, like `///` doc comments in Rust; blank lines and plain `;` comments may sit in between. The UI matches the open box by its **literal** `R` title, so every documented M291 has a fixed `R"…"` (no `R{…}`) that is unique within the file - z-height suffixes its titles with `· kalt` / `· warm`. The `P` text must still stand on its own: it is all classic DWC and PanelDue show. An M291 without a `;;` block still shows, as plain text, but is not listed as a step.
- **Jinja** in the Markdown and in `description`, `enabled` and `hint`: `{{ … }}` and `{% … %}` against the live object model, globals as `global.<name>` like in RRF (hardened flags compare against 1431655765 / 2863311530). Filters and `range()` only - Nunjucks is no sandbox, so the UI refuses method calls, `constructor`/`__proto__`/`prototype` and includes, and shows such a block unevaluated. Templates are evaluated only in the indexed flow files, never on the text of an open message box, which a job file could otherwise use to run template code.
- **Progress:** before a long wait (heating, probing) an `M291 … S1 T0` shows as a step with a spinner; the next M291 replaces it. Close the last one before the macro ends (`if state.messageBox != null` → `M292`), it stays open otherwise.
- **Cancel:** give cancellable prompts `J2` and restore a safe state yourself on `result != 0` (`sys/meltingplot/z-probe/cancel-calibration.g`) - a cancel that only returns leaves shifted datums or disabled soft limits behind. End with `echo "Error: …"`, so the UI reports the flow as not completed.
- **Images:** `![text](0:/sys/meltingplot/flows/img/<name>.webp)` for shipped images, `0:/sys/overrides/flows/…` for own ones, never under `macros/` (DWC lists every file there as a macro).
- **Own flows** go to `0:/sys/overrides/flows/`, which no config update overwrites (see "Machine-owned files").
- Keep `;;` lines under 200 characters and split a paragraph over several lines; Markdown joins them. `tools/gcode_crc.py` leaves comment-only lines untouched.
- The UI indexes `0:/macros`, `0:/sys/meltingplot` and `0:/sys/overrides/flows` and lists what it found (YAML errors, duplicate titles, refused Jinja, markup DOMPurify removes) on its Service page. A `;;` block in a `sys/` helper documents that helper's prompt wherever it appears, e.g. the door check.

### State Management

Global state is centralized in `sys/meltingplot/globals.g`. Key variables:
- `global.result` — error propagation between macros (0 = success)
- `global.potential_unsafe_state` — blocks operations when unsafe
- `global.machine_mode` — operating mode ("default" or "automatic")
- `global.door_left_open` / `global.door_right_open` — door interlock state
- `global.debug` — enables debug echo messages

### Bit-flip hardened states
The Duet has no ECC RAM and the CE interlock rests on a handful of globals, so **no Tier-1 flag in `globals.g` is a bool** — a bool is one flipped bit away from its opposite. Hardened flags hold one of two int patterns of maximal Hamming distance, `0x55555555` (true) and `0xAAAAAAAA` (false, a uint32 in RRF — verified on the machine); no single, double or triple flip turns one into the other, so a corrupted value is never a valid state. The list, and which pattern is the *permissive* one per variable, is in `sys/meltingplot/globals.g` ("bit-flip hardened states"). Rules:
- **Write** the hex literal: `set global.door_left_open = 0xAAAAAAAA`. There is deliberately no named constant (it would be one more global a flip breaks for every consumer).
- **Read only through the string coercion** against the rendered decimal: `("" ^ global.door_left_open) == "2863311530"` ("closed"), `("" ^ global.door_left_switch_checked) == "1431655765"` ("checked"). `"1431655765"` = 0x55555555, `"2863311530"` = 0xAAAAAAAA. The coercion is what keeps the check alive: a direct `global.x != 0xAAAAAAAA` throws "expected numeric operand" the moment `x` holds a non-number (verified with `set global.x = true`), and an expression error aborts the file — in `daemon.g` that is the safety loop. `"" ^ x` renders any type (RRF meta-command reference, "Literals"), so a bool, null, float or flipped type tag is just one more non-matching string.
- The permissive branch is reachable only by exact equality with the permissive pattern; the restrictive branch is the inequality, so every corrupted value lands there. Never `== true`/`== false`, never a bare `if global.x`, never a numeric comparison against a pattern.
- The string `machine_mode` follows the same rule: gate a permissive action with `("" ^ global.machine_mode) == "automatic"` (or `!= "automatic"` → abort); perform the downgrade on `!= "default"` (trigger4.g, the daemon's `elif`) so a corrupted string still downgrades. `saved_*_heater_state*` likewise: only `"active"`/`"standby"` restore, anything else warns and leaves the heater off.
- `daemon.g` validates the flags that persist between iterations: door states, switch_checked flags or `machine_mode` holding neither valid value halt with M112 (nothing but the daemon and the two operating-mode scripts write them); the Z stall deadline outside `[upTime, upTime+30]` halts through `trigger5.g` (see "Expression triggers"). Numeric timers are plausibility-checked and read as timed out / re-dated with an `M118` warning (`idle_since` in the future, motion timestamps more than 1 s in the future — the slack absorbs the non-atomic `upTime`+`msUpTime` pair, two separate OM lookups whose sum reads up to 1 s low when a second rolls over between them, `idle_heater_timeout` capped at 7200 s, `z_motor_stall_time_max` outside 1..30 arms 5 s).
- Numeric values cannot be coerced (they need `<`/`>`), so a type error there still aborts the daemon. That is why the daemon's block order is fixed: tracker → doors → mirror → hot → mode → LED contain only coerced comparisons and always run; idle cutoff, filament and MFM follow. Do not move a numeric comparison in front of the mode block.
- Every detection sits in a branch that runs only on a transition, a mismatch or inside the motion window; steady-state SPI cost is zero. Never add per-iteration copies or redundant compares.
- `potential_unsafe_state` is collected in the daemon-local `var.unsafe` and written to the global **once per iteration, after the tracker loops** — never reset in place at the top. `trigger4.g` reads the global concurrently on the Trigger channel, and the in-place reset read "safe" during motion until the loop reached the moving axis or extruder: a door opened in that gap ran `default.g` instead of `M112`. The same holds for any other flag a trigger reads: publish the finished verdict, never an intermediate.
- **Confirm every permissive branch with a second, inverse read.** The patterns protect the *value*, not the *decision*: a branch body can also run because the flow that led to it was wrong — a mis-evaluated condition, an EMI blip on the sensor it read, or the flag changing right after it was read. So a branch entered because a Tier-1 flag (or a door sensor) read permissive re-reads it as its first statement with the inverse comparison and takes the restrictive path on disagreement. Every global/OM access is its own lookup (an SPI round trip on the SBC), so the confirm is a genuine second sample. Two constraints: it may only ever move the outcome toward the **restrictive** side — never confirm a downgrade, a heater cutoff or a halt into a permissive outcome (the one exception is `trigger4.g`, which re-reads the *sensors* before the downgrade to reject EMI, and where the daemon performs the downgrade anyway) — and a disagreement **warns (`M118 P0`) and stays restrictive, it does not halt**: an operator can open a door in the window between the two reads, and that legitimate race must not fire M112. Only a value that is neither pattern is provable corruption, and that is what halts. Guard-style consumers (`if ("" ^ global.machine_mode) != "automatic" → abort`) carry their permissive branch in the fall-through, so their confirm is the same guard written a second time with its own message. Confirmed sites: the daemon's door-edge `switch_checked` credit and its mode upgrade, `reload-operating-mode.g`, `trigger3.g`, the wait-loop exits in `print/prepare.g` and `ce-declaration/doors/ensure-checked-closed.g`, `print/finish.g`'s retract and park gates, and the mode guards in `start.g`, `print/prepare.g`, `clean.g` and in every user macro that moves or heats (`load-filament`, `unload-filament`, `calibration/e-steps`, `calibration/nle`, `calibration/pressure-advance`, `calibration/z-height`, `drive-cleaner`, `calibration/align-z-axis`, `calibration/heightmap`, `calibration/magnetic-table`, `startup/heatup-and-home`). Every macro under `macros/` that moves, extrudes or heats also refuses to start while a job file is being processed (`job.file.fileName != null`; the filament and nozzle maintenance macros allow the `"paused"` state), because default mode switches the heaters off and limits speed to 60 mm/min and a running print owns the motion queue.
- In DWC the flags show as 1431655765 / 2863311530. Audit before committing: `grep -rnE "[^^] *global\.(door_left_open|door_right_open|potential_unsafe_state|machine_is_hot|door_left_switch_checked|door_right_switch_checked|sensorless_z_homing|closed_loop_homing|idle_heater_pause_hold|idle_heater_cutoff_done|z_motor_stalled|machine_mode|saved_bed_heater_state|saved_tool_heater_states)(\[[^]]+\])?\s*(==|!=)" sys macros` must return nothing.

### Background Monitoring

`sys/daemon.g` runs continuously, monitoring door states, stall events, temperatures, and LED status. **New monitoring goes into an expression trigger, not into `daemon.g`, whenever a trigger can express it**, and a daemon block that fits moves out when it is touched (see "Expression triggers (M581.1)"). Every daemon line costs SPI round trips, a trigger expression none: moving T5–T8 out saved 20–40 ms of daemon cycle time, and the daemon does not get slower from the triggers (87 ms with T5–T8, 88 ms without, measured 2026-09-24). The daemon keeps what a trigger cannot do:
- sample streams: comparing against the previous sample, a running maximum, a window over samples (motion tracker, MFM swing detection, pause melt-zone peak)
- anything that reads `var.*`: the `switch_checked` mirror, hence the door credit and the mode upgrade
- anything that would fire periodically while idle: the idle heater timer

A trigger is not free either. It costs main-loop time on the Duet on every pass (see the cost bullet there), so move a block only when its guard is cheap. Otherwise the saving on the daemon side is paid for in the main loop.

## Duet G-code Reference

Official docs: https://docs.duet3d.com/en/User_manual/Reference/Gcodes and https://docs.duet3d.com/User_manual/Reference/Gcode_meta_commands — always consult these rather than guessing about RRF G-code behavior.

### Meta Code Programming
RRF extends standard G-code with meta commands that provide programming capabilities. Supported constructs: `var`/`global`/`set` for variable declaration and assignment, `if`/`elif`/`else` for conditionals, `while` for loops (with `break` and `continue`), `echo` for output (including file redirection with `>`, `>>`, `>>>`), and `abort` to terminate all nested macros and the current print. Block structure is **indentation-based** — the body of `if`, `elif`, `else`, and `while` must be indented from the keyword, and the block ends at the first non-indented line. Available types are bool, int, float, string, DateTime, object, and array. Expressions support arithmetic, comparison, boolean (`&`/`|`/`!`), string concatenation (`^`), length (`#`), and ternary (`? :`). Built-in functions include `abs`, `ceil`, `cos`, `exists`, `fileexists`, `fileread`, `find`, `floor`, `max`, `min`, `mod`, `random`, `round`, `sin`, `sqrt`, `vector`, among others. Note: `*` (multiply) only works inside `{ }` expressions since `*` normally introduces a checksum in G-code. Meta-keyword arguments (everything after `if`/`while`/`set`/`echo`/…) are limited to **255 characters** — RRF aborts with "Keyword argument too long (> 255)". Split long conditions, e.g. hoist a common path prefix into a `var` first; keep long command lines (M118/M291 messages) well under 255 too.

### Input Channels
RRF processes G-code from multiple independent input channels: USB, HTTP (DWC), PanelDue/UART, Telnet, SD card (file), second UART, MQTT Client, and second USB. Each channel maintains **its own independent state** for: feed rate, arc plane (G17/G18/G19), units (G20/G21), absolute/relative positioning (G90/G91), feed rate mode (G93/G94), extruder abs/rel (M82/M83), and volumetric extrusion (M200). At the end of `config.g`, these states are copied to all channels. When a macro runs, the channel state is saved and restored on return — but changes made during job files persist for the session.

The channel distinction matters for:
- **Command queueing:** Deferred queueing of certain non-movement commands (M106, M104, M568, etc.) only applies to the File channel (job files), not commands sent interactively via HTTP/USB.
- **`echo` output:** `echo` only sends output back to the input channel it was called from. To send messages to a specific target (DWC, USB, PanelDue, MQTT), use `M118` with the P parameter (P0=generic/all, P1=USB, P2=PanelDue, P3=HTTP, P4=Telnet, P5=second UART, P6=MQTT, P7=second USB).
- **Channel blocking:** A blocking command (e.g., M109, M190) on one channel blocks only that channel. To cancel, M108 must be sent from a different, unblocked channel.
- **Triggers:** Trigger macros (sys/trigger#.g) execute without waiting for queued moves to complete — use `M400` at the start of trigger macros if synchronization is needed.
- **Never select a tool (`T`) from a trigger macro or `daemon.g`.** A blocking `M291` releases the movement lock (`UnlockMovement`, RRF `GCodes7.cpp`), so a trigger runs while another channel waits in a prompt inside `tpre0.g`/`tpost0.g`, and RRF keeps the target of a tool change per motion system (`ms.newToolNumber`), not per channel — a `T` there re-targets the pending change. This happened: `trigger3.g`'s heater restore (`T T0 P0` … `T T-1 P0`) made the DWC filament load after a boot end with no tool selected, and `M701` failed with "No tool selected". Restore a heater with `M568 P<tool>`, which needs no selection.

### Command Queueing and Execution Order
RRF maintains a **move queue** (look-ahead buffer) for G0/G1/G2/G3 movement commands, and a **deferred command queue** for certain non-movement commands. Together these operate as a single logical queue. Commands from job files and macros are queued — meaning they are acknowledged immediately when placed in the queue, not when executed. This has important implications:

- **Always queued:** G0, G1, G2, G3 moves (except homing/probing moves which are special).
- **Queued when from a file** (and parameters contain no `{ }` expressions): M3, M4, M5 (non-laser), M42, M104, M106, M107, M117, M140, M141, M144, M280, M300, M568, and G10 (without L, with at least one P/R/S/axis parameter).
- **Wait for movement to stop:** Configuration commands (M93, M906, M201, M569, etc.), probing commands, G4, M400, and T commands. These drain the queue before executing.
- **Never queued:** Meta commands (`echo`, `if`, `set`, etc.) execute immediately and do not interact with the queue.
- **Forcing synchronization:** `M400` waits for all queued moves to complete (clears the queue). Use it when subsequent commands depend on motion being finished — e.g. before reading positions, checking sensors, or evaluating conditions that depend on physical state.
- **Bypassing the queue:** If a normally-queued command contains a parameter with an Object Model expression in `{ }`, it is **not** queued because the expression value may change and cannot be evaluated in queue context.

### File Inclusion (M98)
`M98 P"filename"` runs a macro. Relative paths default to `/sys`. Absolute paths use `0:/` (SD card root). Parameters are passed as additional G-code letters: `M98 P"macro.g" S100 Y"string"`. Inside the macro, access via `param.S`, `param.Y` (single uppercase letter). P and R are reserved — M98 consumes R itself as its pause-allowed flag, so an R argument silently never reaches `param.R`. Use `exists(param.S)` to check if provided. A command invoking a macro must be the last command on its line.

### M99: Early Return from Macro
`M99` returns from the current macro early. Not required at end of file — macros naturally return at EOF.

### Variables
- **Global:** `global <name> = <expr>` to declare, `set global.<name> = <expr>` to assign. Persists across macros.
- **Local:** `var <name> = <expr>` to declare, `set var.<name> = <expr>` to assign. Scoped to the current block.
- **Parameters:** `param.<letter>` — single uppercase letter, from M98 call.

### Named Constants
- `result` — firmware built-in: 0=success, 1=warning, 2+=error, -1=M291 cancelled/timed out. Set after each G/M/T command. Meta commands do not change `result`.
- `iterations` — completed loop iterations (0-based) for innermost `while` loop.
- `input` — most recent M291 message box input (modes 4-7).
- `line` — current line number in executing file.

### Error Handling
Two distinct mechanisms are used in this codebase:

**Firmware `result`** — check after G/M commands:
```gcode
G32
if result != 0
  echo "Error: bed leveling failed"
  abort
```

**Project `global.result`** — cross-macro error propagation:
```gcode
set global.result = 0
M98 P"0:/sys/meltingplot/ce-declaration/doors/wait-closed.g"
if global.result != 0
  echo "Error: doors not closed"
  M99
```

### Loop Safety
`while` loops should include an `iterations` guard to prevent infinite loops (no way to break out except machine reset):
```gcode
while condition
  if iterations > 200
    echo "Error: timeout"
    break
```

### Expressions
Use `{ }` for expressions inside G-code commands: `G1 X{move.axes[0].max - 10}`. The `^` operator concatenates strings. The `#` operator gives array/string length.

### daemon.g
`sys/daemon.g` is executed repeatedly by the firmware as a background loop. It should contain a `while true` loop to avoid reopening the file every 10 seconds.

**NEVER use blocking / movement-synchronising commands in `daemon.g`.** The daemon is the machine's safety loop (door interlock, unsafe-state halt, temperature/idle/stall monitoring). Any command that waits for motion to finish freezes the *entire* loop until the print's motion stops — so during a print the daemon is dead for minutes, all safety checks included. Worse, on unblocking it runs one iteration with stale motion-tracking state (`motion_axis_pos`, `motion_axis_time`, `var.now` frozen at the block time), which reads as a huge position jump → `potential_unsafe_state = true` → if `print/finish.g` has meanwhile flipped the door switches, the mode logic fires `M112` (emergency stop). This actually happened: an `M92` issued from the daemon froze it for 44 s until print end, then emergency-stopped the machine and dropped all CAN boards. Forbidden here: anything that calls `LockAllMovementSystemsAndWaitForStandstill` — `M92` (steps/mm), `M201`/`M203`/`M204`/`M205`, `M569`/`M906`/`M913`, `G4` dwell, `M400`, probing/homing (`G28`/`G30`/`G32`), `T` tool changes, `M109`/`M190`/`M116` waits. Allowed: object-model reads, `set`/`if`/`while`/`echo`, and non-blocking deferred commands (`M220`, `M221`, `M104`/`M140`/`M568`, `M106`, `M117`/`M118`, `M291` with non-blocking `S0`/`S1`), and `echo >` into a file — only the spool tracker's `spool<tool>.g`, only while not printing, at most once a minute. Anything that must run at standstill (e.g. applying an e-steps correction) has to be deferred to a context that may block — a pause/trigger macro or the operator — never the daemon.

### The mode-downgrade window — no position-perturbing commands after the settle
The daemon's motion tracker flags `potential_unsafe_state` on **any exact change** of a reported position (`move.axes[].machinePosition`, `move.extruders[].position` compared with `!=`) — physical motion is not required. Commands that rewrite steps/mm, positions, offsets or transforms perturb these values by at least a float/rounding epsilon: `M92` (verified in RRF source — `AdjustEndpoint` rescales the step endpoint via `lrintf(steps * ratio)`; at ~1e8 extruder steps after a long print a float ULP is 16 steps, i.e. hundredths of a mm), `G92`, `G10 L2`/`L20`, `T` tool changes (inverse-transform switch), `M290`, `G29`/`M375`, `M579`. Mid-print this is harmless — doors closed, `switch_checked` true, the automatic branch ignores unsafe state. **Fatal is the combination with the mode downgrade:** clearing `door_*_switch_checked` while `machine_mode` is still `"automatic"` and unsafe state is set fires `M112`. Rule for every sequence that ends by clearing the checked flags (`print/finish.g` is the canonical one, reached from the job end-gcode, `stop.g` and `cancel.g`): all position-perturbing commands run **before** the `M400` + `G4 S1` settle, so the daemon's 0.25 s motion window expires while the flags are still true; between the settle and the flag clear only meta commands (`set`/`if`/`echo`) and position-neutral M-codes (`M106`, `M118`, `M568`, `M140`) are allowed. Never append code to the tail of `print/finish.g` without checking this — the settle is the boundary, not the end of file. This actually happened 2026-08-22: the `M92 E{baseline}` restore, placed after the settle, emergency-stopped the machine at print end after 22 h; the fix was moving it before the settle, not changing the command.

### Expression triggers (M581.1)
RRF 3.7's `M581.1` fires `sys/trigger<N>.g` when an object-model expression turns true. Deadlines on a global run this way instead of in `daemon.g`, set up in `config.g` — not CE; the e-stop and door triggers 2–4 are set up in `ce-declaration/`: **T5** `trigger5.g` Z stall watchdog (a process function: a Z motor that keeps driving against its stop breaks the bed's joints), **T7** `trigger7.g` MFM suppression expiry, **T8** `trigger8.g` print tick every 60 s while printing (spool booking, MFM flow-bias sample). No expression contains a string literal (see the cost bullet); T7 and T8 gate on the job and check "processing" in their macro (see the `R1` bullet). T6, the MFM speed restore, was removed with the MFM speed backoff (2026-09-24). Semantics verified in RRF source (`TriggerItem.cpp`, `GCodes::CheckTriggers`, `RepRap::GetStatusIndex`):
- RRF evaluates each expression itself on every main-loop pass — no SPI round trip and no daemon line, but main-loop time, and the string is parsed again on every pass. `R1`/`R2` do not skip the evaluation (only `R-1` does), so the cheap, usually-false guard goes first; `&&`/`||` short-circuit.
- **What a trigger costs.** Measured 2026-09-24 at idle as `M122` "fastest loop": 0.09 ms with no trigger, 1.0 ms with T5–T8 on firmware mp.4, 0.36 ms with T5, T7 and T8 on mp.5 without string literals.
  - Base cost per trigger: ~0.02 ms.
  - Parsing: ~0.7 µs per character, including a short-circuited part.
  - One OM value: ~0.07 ms.
  - One `global.` reference: ~0.05 ms wherever it was declared (firmware mp.5: 0.05 ms at the head of the list, 0.06 ms at the tail of 81). RRF keeps the globals in a linked list and searches it linearly (`VariableSet::Lookup`); `InsertNew` puts every new global at the head, so the global declared last in `globals.g` is found first. Up to mp.4 the search fetched the name of every entry under the heap lock, and the tail cost 0.34 ms; mp.5 (ReprapFirmware `e655be4c9`) compares an FNV-1a hash of the name first.
  - A string literal costs almost no loop time (+0.01 ms) but is copied into the 2 KB string-heap blocks on every pass, even in a branch that is not evaluated: `ExpressionParser` parses `"…"` without the evaluate flag, so guard order does not help. The copy is garbage at once. One literal trigger raises the garbage-collection rate from ~1/s to ~22/s; T7 and T8 with `""processing""` ran at ~19/s and 0.42 ms, without the literal at ~1/s and 0.36 ms. A GC compacts the heap under the write lock.
  - "Only while processing" needs no literal: gate on the job (`R1`, or `job.file.fileName != null` in the expression) and check `state.status == "processing"` in the trigger macro (see the `R1` bullet). A global in place of the literal was slower on mp.4 (0.30 ms at list depth ~28 against 0.18 ms), and it turns a constant into a mutable global that could silently stop the trigger if it changed.

  Rules that follow:
  - No string literal in an expression.
  - Count the evaluated `global.` and OM references; the guard reads one of them.
  - Keep the expression short.
  - A new periodic task on the same cadence joins an existing trigger's macro instead of adding an expression.

  Whether the slower main loop limits the G-code rate during a print is not measured yet.
- It fires on false → true only. An edge while the `R` condition is not met is lost, and an expression that stays true never fires again — a trigger cannot keep a running maximum, a time window or a sample stream; those stay in the daemon. `M581 T<N> R0` samples the expression again as its initial value (already true → no fire); `M582 T<N>` forces a level check.
- One trigger macro runs at a time, on the Trigger channel, lowest pending number first, never pre-empted. `trigger3.g` holds the channel for up to ~3 s on every door close (`M400` + `G4 P500` loop), and every other trigger macro — `trigger4.g` included — waits behind whatever runs, so keep trigger macros short. T0 is the only exception: it is an emergency stop inside the firmware, with no macro, even while another trigger runs. T1 is handled in the firmware too: it pauses a running print, with no macro. A new trigger therefore takes a free number: T6 or T9 and up (MaxTriggers is 32 on the MB6HC).
- Delete a trigger with `M581 T<N> P-1`. In SBC mode `M581.1 T<N> P-1` left the trigger in place (2026-09-24). `M581 T<N> R-1` / `R0` switches it off and on for a measurement.
- `var.*` and `param.*` read as **null, without an error** (there is no GCodeBuffer). A trigger cannot see the daemon's private `switch_checked` mirror — which is why the mode upgrade can never become a trigger: it would fire the moment someone assigns `door_*_switch_checked` in the console, before the daemon reverts it.
- An evaluation error disables the trigger for good ("Trigger N disabled", reported on every channel). Read Tier-1 flags through `"" ^` here as everywhere.
- `R1` means "a job is loaded" (`PrintMonitor::isPrinting`, the same condition that makes `job.file.fileName` non-null), which stays true while pausing, paused, resuming and cancelling. A trigger that may act only while "processing" gates on the job and checks the status in its macro, never with a literal in the expression. `R` is checked only at the edge, so when the rest of the expression is already true outside a job (T8's 60 s timer runs out during idle), the job goes into the expression as `job.file.fileName != null`: with only `R1` the edge falls into idle, and the expression is still true at the job start and never fires. A guard that is false outside a job (T7's `mfm_suppress_until`, cleared by `print/finish.g`) makes `R1` enough.
- A running trigger macro makes `state.status` read `"busy"` (`DoingFileMacro()` exempts only the daemon's channel), and busy restarts the daemon's idle heater timer (`idle_since`). Pausing, paused, resuming, cancelling and processing outrank busy (`GetStatusIndex`), so a trigger macro during a job leaves the status alone. **No trigger may fire periodically while the machine is idle** — it would keep the idle heater cutoff from ever firing; a trigger on "the status became idle" would even re-fire itself.
- A trigger macro whose action is not a halt re-checks its condition as its first statement: another trigger can run in front of it, and the condition can change in between (an extended suppression window). A halt (`trigger5.g`) does not — it is never confirmed into a permissive outcome — and builds its message without anything that can throw before the `M112`. A macro that skips its action because the status is not "processing" re-arms its own trigger: the fire used up the edge, and an expression that stays true never fires again. `trigger8.g` moves `spool_track_time` on before its status check; `trigger7.g` moves the end of an expired suppression window 10 s out (in one `set`, so a clear or re-base on another channel is never overwritten). Both therefore fire every 60 s or 10 s during a pause and do nothing else.
- The expression is a quoted string parameter: a quote inside it would be doubled (`""text""`, but see the cost bullet), the expression is at most 255 characters, and an `M581.1` line carries no trailing comment (G-code line limit 256).
- **A string literal in an expression needs the Meltingplot firmware `3.7.0-rc.1+3-mp.4` or later.** Before it, such an expression deadlocked the main task: `TriggerItem::EvaluateExpression` parsed through `StringHandle::Get()`, which holds the heap read lock, and the literal's `StringHandle` then waited for the write lock for ever. In SBC mode the SPI link went quiet and the board reset after 20 s ("StuckInSpinLoop, Gcodes spinning") — on 2026-09-23 that left the machine without `config.g` and with `daemon.g` failing on its first global. The fix copies the expression before parsing (ReprapFirmware `e5e93912c`). Since 2026-09-24 no expression contains a literal; the lookup costs above are those of mp.5.

### Setting Tool Temperatures
Prefer `M568 P<tool> S<active> R<standby>` over the legacy `G10 P... S... R...` form — G10 is overloaded (tool offsets L2/L20, retraction), M568 is the dedicated RRF 3.3+ command and also controls the heater mode (`A0`=off, `A1`=standby, `A2`=active; without `A` only the setpoints change). Whenever an active heater is required, pass `A2` explicitly: selecting a tool (`T0`) activates its heaters only as a side effect, and neither G10 nor an A-less M568 changes the heater mode — never rely on the tool-selection side effect to have the heater active.

### Comment Style
Scripts start with a brief description comment. Inline comments explain hardware-specific M/G-code parameters. From RRF 3.6.0, comment indentation is no longer significant.

### Filament Loading and DWC Interaction
The RRF filament system predates meta G-code, creating timing constraints. Key issue: `move.extruders[n].filament` in the Object Model is NOT updated until `load.g` completes, so `load.g` cannot query its own filament name.

**DWC filament load sequence:** `T0` (tpre0→tpost0→M703, but no filament name yet) → `M701 S"name"` (load.g runs, OM updates after) → `M703` (config.g runs, OM is now correct). Only the final `M703` → `config.g` has the correct filament identity.

**Deferred loading pattern:** a profile's `load.g` is a single call to the shared wrapper `sys/meltingplot/filament/on-load.g` (`M98 P"0:/sys/meltingplot/filament/on-load.g" F"<name>"`), which reads temperatures from `temps.g`, sets them and arms `global.filament_load_pending[state.currentTool]`, then exits without physically loading. The centralized `sys/meltingplot/filament/on-config.g` (run from the machine-generated `config.g` — the only post-M701 hook) consumes the flag and calls `filament/load-procedure.g`; it records the dispatched filament in `global.filament_load_dispatched` BEFORE clearing the flag (watchdog race ordering — keep it that way). `unload.g` is likewise one call to `sys/meltingplot/filament/on-unload.g`. A failed physical load is handed to `daemon.g` in `global.filament_load_failed`, set once at the end of `filament/load-procedure.g`, after its last decision: the daemon drops the assignment (`M702 P0`) and clears the flag within one cycle, so the load decides on the local `var.load_failed` and never reads the global back (it did, and the daemon's clear made a failed load run the e-steps calibration and leave the heater on).

**`abort` is forbidden in the filament load/unload path.** `abort` terminates all nested macros *and the current print file* — so a broken filament profile, a missing `temps.g` or a stray console `M701`/`M702` would kill a running job over a configuration error. `filament/on-load.g`, `filament/on-unload.g` and everything they call warn and return instead: `M118 P0 S"Error: …"` (P0 reaches every channel; `echo` only answers the calling one) followed by `M99`. Returning early is the safe outcome, not a silent one — the load path bails out before arming `filament_load_pending`, and the unload path before the physical unload, which is exactly the signature the broken-profile watchdog in `daemon.g` detects, reports and cleans up.

**Machine-owned profile files:** `filaments/<name>/config.g`, `load.g` and `unload.g` are auto-generated boilerplate — never hand-edit them. `tpost0.g` regenerates all three via `sys/meltingplot/filament-profile/regenerate.g` on every tool change with an assigned filament; a missing `config-override.g` is created by renaming the existing `config.g` (M471), which auto-migrates foreign/DWC-created profiles. The helper must only run in blocking-capable contexts (tpost0, macros), never in `daemon.g`. Per-material data lives in two user-editable files: `config-override.g` (M572/M207/M143/M309/…) and `temps.g` (sets `global.filament_temp_active`/`_standby`/`_unload`; `_unload = 0` means "unload at active temp"; the optional `_bed` is read only by `startup/preheat`, which falls back to `global.preheat_bed_temp` when no loaded profile sets it - the shipped profiles have none). `temps.g` exists because the temperatures can neither live in the machine-generated `load.g`/`unload.g` (RRF cannot read values back out of G-code files, so regeneration would lose them) nor be passed as an `R` parameter (M98 consumes R as its pause flag — the pre-`temps.g` `S<active> R<standby>` form silently always used standby 160). `load.g`/`unload.g` are only regenerated once `temps.g` exists; for foreign profiles it is created by the `repair-filament-profile` macro (prompted temps). A brand-new profile is created by `macros/meltingplot/maintenance/create-filament-profile` (prompts name, temperatures and the print parameters, writes every file, then calls the regenerator).

**Nozzle diameter and nozzle-specific profile data:** a profile describes a *material*, not a material/nozzle combination — there is one `PLA` profile, not `PLA 0.4mm` and `PLA 0.8mm`. The installed nozzle is a property of the **tool**: `global.nozzle_diameter[tool]` is declared in `globals.g` and persisted per tool in `sys/generated/nozzle<tool>.g`, written by the shared `sys/meltingplot/hardware/store-nozzle-diameter.g` (`D<diameter> T<tool>`, hands the two-decimal key back in `global.result`) and loaded by `globals.g` (fileexists-guarded) — a nozzle change must survive a power cycle. Three callers ask for the value: the `macros/meltingplot/maintenance/set-nozzle-diameter` macro, `calibration/e-steps` when run as a macro (it calls `hardware/confirm-nozzle-diameter.g` before measuring; the load path passes `C0` because it has already asked), and `sys/meltingplot/hardware/confirm-nozzle-diameter.g`, which `filament/load-procedure.g` runs at the feed prompt — after a filament change was triggered but **before** `calibration/e-steps` — as a dropdown with the configured diameter preselected, so the nozzle-specific calibration files are never written under a stale key. Cancelling it keeps the configured value (`J2`, never `J1` — the confirmation must not abort a load), and a changed diameter is re-applied with `filament-profile/apply-nozzle-file.g`, **not** `M703`: that macro runs from inside the profile's own `config.g`, so `M703` would re-enter the executing file. Like `last-filament-temp.g` these files are machine-local state: they are written on the machine into `sys/generated/`, never shipped with the repo, and a config update never overwrites them.

**Other machine-state globals** follow the same pattern (declared in `globals.g` with a "nothing known yet" default, overwritten at boot by a fileexists-guarded machine-local file in `sys/generated/` that a confirm macro (`hardware/confirm-*.g`, `spool/confirm.g`) writes on change, gitignored): `global.nozzle_type[tool]` (key string: `brass`, `cht`, `hardened`, `cht-hardened`, `tungsten-carbide`, `copper`, `other`, `unknown`; file `nozzle-type<tool>.g`, asked by `set-nozzle-diameter` after the diameter via `hardware/confirm-nozzle-type.g`), `global.filament_diameter[tool]` (mm, default 2.85; file `filament-diameter<tool>.g`, macro `set-filament-diameter` via `hardware/confirm-filament-diameter.g`, which also re-applies `M200`; `config.g` reads it for `M200`/`M404`, it is the first half of the calibration key, and `calibration/nle` and the spool tracker use it), the spool state `global.spool_net_weight[tool]` / `spool_remaining[tool]` / `spool_tare[tool]` / `spool_density[tool]` (grams, grams, grams, g/cm³; one file `spool<tool>.g` written from the globals by `spool/store.g`; asked at the feed prompt of every load right after the nozzle diameter via `spool/confirm.g A1` and by macro `set-spool-size`) and the machine-wide `global.bed_surface` (key string: `pei`, `pei-textured`, `pertinax`, `g10`, `carbon`, `glass`, `other`, `unknown`; file `bed-surface.g`, macro `set-bed-surface` via `hardware/confirm-bed-surface.g`). None of these keys builds a file name. Every prompt is a dropdown with the configured value preselected and cancels with `J2`, keeping the value. The key list inside each confirm macro must stay in the same order as its `M291 K` list.

**Material data and filament consumption:** a third user-editable profile file, `filaments/<name>/material.g`, sets `global.material_density` (g/cm³) and `global.material_spool_weights` (net grams of every spool size the material comes on, written as `{1000,2500,}` — the trailing comma keeps a one-element list an array in 3.5/3.6 syntax, verified in RRF `ExpressionParser::ParseGeneralArray`; `vector(0, 0)` = unknown, `[]` needs 3.7). The empty-spool weight (tare) is **not** a material value — it belongs to the spool body, and two 2.3 kg spools of different make weigh differently when empty — so it lives in the machine-wide spool catalog `global.spool_catalog = {"Pappe",500,"PC",350,"PE",450}` — a **flat** list of pairs (spool type i: name at `[i + i]`, tare at `[i + i + 1]`; flat because that is what `fileread()` returns), declared with the default list in `globals.g` and replaced by the machine's own list in `sys/overrides/spool-catalog.csv`: one CSV line `"Pappe",500,"PC",350`, read by `sys/meltingplot/spool/read-catalog.g` with `fileread(file, 0, 40, ',')` (RRF 3.5+). A CSV line is not bound by the 255-character command limit; the limit instead is `MaxFileReadArrayElements = 40` per call (RRF `Configuration.h`) — RRF 3.6 cannot concatenate arrays to page further (`^` on arrays needs 3.7) — so **at most 20 spool types**; the loader warns about a longer file (it reads element 41 and tests it for null — on an SBC, DSF evaluates `fileread` itself (`Functions.cs`) and returns `{null}` where standalone RRF returns an empty array, so never test the length of a `fileread` result for "nothing read") and replaces empty fields (null) by `""`/0. The file is written by macro `macros/meltingplot/maintenance/edit-spool-catalog` (menu: add a name + tare, remove an entry; every change deletes the file with `M472`, appends every entry with `echo >>>` — no newline, so no string-expression limit either — ends the line with `echo >>` and reads it back) or edited in DWC; a name must not contain `"` (it would need doubling, RRF has no string replace), and the file must not carry a comment line. The file is **not** read at boot but by its readers (`spool/confirm.g`, the macro): an edit applies at once, and a mistake in a hand edit can only break the spool prompt, never `globals.g`. `spool/confirm.g` asks three things: the net weight (the profile's sizes as the dropdown — `M291 K{var.labels}`, RRF reads K as an expression and takes any string array, verified in `GCodes7.cpp`; the command shape is the proven one of `hardware/confirm-nozzle-diameter.g`, only the K operand is a variable instead of the literal list — else the generic size list), the spool body from the catalog (preselected by the tool's current tare, "Other..." or an empty catalog asks the tare as a number; the tare is copied to `spool_tare[tool]`), and the weight on a scale, from which it subtracts the tare itself (without a known tare the prompt asks for the filament weight directly). It is written by `sys/meltingplot/filament-profile/create-material-file.g` (prompts; returns 1 in `global.result` when the file exists or the operator declined, 0 when written), offered at the load prompt by `spool/confirm.g` and by the `create-filament-profile` / `repair-filament-profile` macros, and it is never executed by the generated `config.g` — `spool/confirm.g` runs it itself — reset, run and take `material_density` / `material_spool_weights` into locals as consecutive steps with no prompt in between — then stores the density on the tool (`spool_density[tool]`), so the tracker never depends on which profile ran last. The two globals are a **transfer channel shared by both tools**, not state (T0 and T1 may hold different materials and load in different motion systems at the same time); nothing else may read them. Consumption is booked by `sys/meltingplot/spool/track.g` from `move.extruders[].position`, the extruder motor position in mm (verified in RRF: the OM `position` is `LiveMachineCoordinate`, `Move.cpp`; only `StartPrinting` zeroes it, `GCodes.cpp` — at every job start, right before `start.g`; `G92 E` only sets the virtual position). It holds everything the motor fed — print moves, retractions and every macro, console and DWC extrusion (load, purge, prime, e-steps/NLE/PA calibration, MFM recovery) — with M221 already applied. `rawPosition` is no source for the spool: it counts only moves outside macros (`!gb.IsDoingFileMacro()`), and nothing outside a job would be booked. grams = mm · π · (d/2)² · density / 1000, booked **with sign**, so a retraction nets against its un-retract and a sample taken mid-retraction is corrected by the next one — except the unload: `filament/unload-procedure.g` shifts the baseline by its 200–300 mm retraction, which books nothing, because it pulls back filament that was never booked (hand-fed through the tube; the motor only fed the ~65 mm from gear to nozzle, whose molten end is cut off — crediting it would overstate the spool by 1–2 g per unload). The shift, not a re-base, cancels whatever `daemon.g` books during the unload, in either order. `trigger8.g` (expression trigger T8) calls it every 60 s while processing (OM reads and `set` only), `daemon.g` outside a print when the extruder stops — the motion tracker's extruder delta still non-zero after its 0.25 s window is that edge (read coerced in the tracker block, the booking itself runs in the numeric tail) — and while not printing writes `spool<tool>.g` (`W1`) at most once a minute, so a power cycle loses at most the last minute. `print/finish.g` calls it with `J1` before the settle: book, write and report what is left. The job-start zero is never booked as a retraction: `start.g` re-bases the baseline to 0 before anything extrudes, and `track.g` also takes a jump to exactly 0 as the reset (the moment before `start.g`, and a power-fail resume, which runs no `start.g`); the baseline is advanced before the booking, so two concurrent calls can double-book only between two consecutive lines. **`print/finish.g` runs twice at a normal job end** — the end G-code, then `stop.g`, which RRF runs after every finished print (`GCodes4.cpp`, state `stopping`): both calls book and write, the second finds nothing new; `start.g` arms `global.spool_report_pending` and the first flush clears it, so what is left is reported once. `spool/confirm.g` re-bases the baseline when a spool is entered (the scale weight already reflects everything extruded before). Density 0 means the tool is not tracked. `print/prepare.g` converts the slicer's estimate per tool (`job.file.filament[i]` = slicer extruder i = tool i) to grams and warns once for all tools (`M118` + one non-blocking `M291 S1`, a second would replace the first) when it exceeds the remaining weight — it never blocks, automatic-mode jobs start unattended. In copy/mirror mode the slicer lists one extruder that both tools extrude, so only tool 0 is checked there; the tracker still books both spools (it reads the position of each extruder drive).

**Never concatenate the raw diameter into a file name.** RRF keeps the decimal places the value was written with: `0.4` renders `"0.4"`, `0.4000` renders `"0.4000"`, and any computed value renders `"0.4000000"` — three different, silently wrong file names for the same nozzle. The hardware key is `"<filament>-<nozzle>"`, both as fixed-width two-decimal strings (`sys/meltingplot/lib/format-number.g` with `D2 W0`), filament first so a directory listing groups the 2.85 and the 1.75 files: `M98 P"0:/sys/meltingplot/filament-profile/calibration-key.g" T<tool>` → `"2.85-0.40"`, `"1.75-1.20"`. E-steps, NLE, PA, retraction and heater feedforward all depend on the filament diameter as much as on the nozzle (different extruder gears; 2.65× the volume at the same filament speed), so every writer builds the name from that key and every reader resolves it through `sys/meltingplot/filament-profile/find-calibration-file.g S"<name>" F"<base>" T<tool>` (base = `config-auto-esteps`, `config-auto-nle`, `config-auto-pa`, `nozzle`), which hands back the first existing path of the chain `<base>-<filament>-<nozzle>.g` → `<base>-<nozzle>.g` **only while the tool runs 2.85 mm** (every file of that era was measured with 2.85 mm; on a 1.75 mm tool it would be a silent wrong hit) → `<base>.g`, or `""`. Both helpers return through `global.result` (RRF macros cannot return a value). **`global.result` is only valid immediately after the call that set it** — no macro saves or restores it, and none may assume it survives an intervening call. A macro that needs an error code captures it into a local `var` on the very next line (see `filament/load-procedure.g` around the `calibration/e-steps` call); a macro that produces one sets it explicitly. Everything that depends on the nozzle lives in `filaments/<name>/nozzle-<key>.g` (max volumetric flow rate, M572, M207, M309); the machine-generated `config.g` runs `config-override.g` first and then `sys/meltingplot/filament-profile/apply-nozzle-file.g S"<name>"`, which picks `nozzle-<key>.g` of the current tool if it exists, so nozzle values override material values. That selection deliberately sits in a static macro rather than being emitted into `config.g`: keep the generated `config.g` to plain `M98` calls. Meta code (`var`/`if`) written by `echo` needs quotes inside quotes, exists only on the machine and is reviewable nowhere, so a quoting mistake in it is invisible in the repo and breaks all 30 profiles at once — while the same logic in a static macro is ordinary, diffable source. A missing `nozzle-<key>.g` is not an error — the material-wide values from `config-override.g` then stand, which is what keeps profiles predating the split working. It is nevertheless *offered* rather than merely tolerated: `sys/meltingplot/filament-profile/create-nozzle-file.g` asks whether to add the values for the installed nozzle (enter them, write defaults, or not now) and writes the file, handing back `0` in `global.result` when it wrote one so the caller can apply it with `filament-profile/apply-nozzle-file.g`. That offer is called only from the interactive paths — `hardware/confirm-nozzle-diameter.g` (at the filament-load prompt, where the operator has just selected the profile and the new values still reach the load and the e-steps/NLE calibrations that follow), `set-nozzle-diameter` after a nozzle change, and `create-filament-profile`, which shares the same prompts instead of duplicating them. It must never move into `filament-profile/apply-nozzle-file.g` itself: that one runs from the generated `config.g` on every `M703`, hence also from `print/prepare.g`, `pause.g`, `resume.g`, `trigger3.g` and the MFM auto-recovery, where a blocking `M291` would stall the print — and the load path already sits at macro nesting depth 7 of the 10 RRF allows. Because M572/M207/M309/flow rate are *global machine state* (whatever the previously loaded filament set stays active), the nozzle file always writes all of them explicitly instead of only the deviating ones.

**Broken-profile watchdog (`daemon.g`):** a DWC-created profile missing the standard lines fails silently (M701 registers the filament, nothing physically loads). Since `fileread()` cannot parse G-code files, detection is behavioral: within 60 s of an OM filament-name change either `global.filament_load_dispatched` must match (load dispatched) or the profile is broken — the daemon then distinguishes load.g vs config.g failure via the stuck deferred flag, warns (M291 S1 + M118, naming the missing line and the `repair-filament-profile` macro), captures the name in `global.filament_broken_profile`, and force-unloads: `global.filament_unload_skip = true` + `M702 P0`. The forced flag makes `filament/on-unload.g`/`filament/unload-procedure.g` return immediately (first-statement guard, which self-clears the one-shot flag so it can never get stuck set), so the daemon's M702 only clears the assignment and cannot block. The name→"" transition without `filament_unload_done` flags a broken `unload.g`. `macros/meltingplot/maintenance/repair-filament-profile` is the canonical fix: it writes `temps.g` (prompted temps, or kept if present) and then regenerates config.g/load.g/unload.g via `filament-profile/regenerate.g`.

### MFM (Rotating Magnet Filament Monitor) — Firmware Semantics
Verified against RRF source (`RotatingMagnetFilamentMonitor.cpp`, `Duet3DFilamentMonitor.cpp`). Config here: `M591 P3 D0 R60:180 E5 L25.3` (tolerance 60–180 %, 5 mm check segment, 25.3 mm/rev sensitivity).

**Ratio / pause trigger is per-segment, NOT cumulative.** Each ~`E`-mm segment computes `lastMovementRatio = (measuredRevs / commandedMm) * mmPerRev`, i.e. `real filament / commanded filament`. `commandedMm` is derived from **e-steps** (`steps / e-steps`). Pause: `lastMovementRatio < R-min` → P=4 (tooLittleMovement), `> R-max` → P=5 (tooMuchMovement). So a wrong e-steps value is a **constant** ratio offset (`e_steps_configured / e_steps_real`), it does **not** mathematically integrate.

**Why long prints false-pause anyway (e-steps error class):** a constant bias parks the baseline closer to the `R`-min/max wall, so normal per-segment measurement noise (slip, backlash, retracts) crosses the threshold eventually — probability of ≥1 false trip → 1 as segment count grows. Statistically inevitable over time, not integration. The transient handlers (swing/oscillation suppression, auto-recovery) do NOT address this systematic class — recovery either falsely "confirms" (reading still biased >50 % → resume → re-trips → loop) or falsely "fails" (biased <50 % → stays paused though filament is fine).

**Remote (CAN/toolboard) computation — verified against `Duet3Expansion/.../RotatingMagnetFilamentMonitor.cpp` (3.6.3-rc.1):** our MFM is on the toolboard (CAN addr 20), so `Check`/`CheckFilament` run **on the toolboard**. The toolboard maintains and **integrates over the whole print** `totalExtrusionCommanded` and `totalMovementMeasured` (accumulated every comparison in the `comparing` state, never reset mid-print). From those it derives `MeasuredSensitivity = totalExtrusionCommanded/totalMovementMeasured` (= `calibrated.mmPerRev`) and `avgPercentage = totalMovementMeasured*mmPerRev/totalExtrusionCommanded*100`, and ships a subset back via `FilamentMonitorDataNew2`→`UpdateLiveData`. **This is where a systematic e-steps/sensitivity error integrates** — every comparison biases in the same direction, so `avgPercentage`/`calibrated.mmPerRev` converge tightly on the bias factor as the print grows.

**Pause trigger is still per-segment, not the integral.** P=4/P=5 fire on `lastMovementRatio = (amountMeasured/amountCommanded) * mmPerRev` per ~`E`-mm segment using the **configured** `L` (NOT `MeasuredSensitivity`). So `calibrated.mmPerRev` is an *output* of the integrating totals, not fed back into the decision. The "inevitable pause on long prints" is the per-segment value on a bias-shifted baseline + measurement noise eventually crossing `R-min`/`R-max` — same root cause as the integral, visible in two places.

**Which OM fields exist remotely:** the whole **`calibrated.*` subtree is gated on `IsLocal()`** (RRF main-board OM table) → **NOT exposed in the main-board OM for remote monitors** (the toolboard still *computes* it internally, it's just not surfaced as `sensors.filamentMonitors[0].calibrated`). Remote-safe OM fields (gated only on `hasLiveData`, populated from the CAN message): `avgPercentage`, `lastPercentage`, `minPercentage`, `maxPercentage`, `position`, `totalExtrusion`. `configured.*` (your `L`/`R`/`E`) lives on the main board, always available.

**Detection signal (remote-safe):** use `avgPercentage` — it equals `mmPerRev/MeasuredSensitivity*100`, i.e. **`avgPercentage` IS the integrated bias factor in percent**, and it's the CAN-transported view of the same integral that backs the (locally-only) `calibrated.mmPerRev`. Systematic bias = `avgPercentage` settling stably away from 100 % once `totalExtrusion` is large enough for the whole-print mean to converge, with a **narrow** `maxPercentage − minPercentage` spread. A real jam looks opposite: sudden drop, high variance, worsening, recovery test fails. Caveat: `min`/`maxPercentage` are **all-time running extremes, never reset mid-print** (post-jam the min stays low forever) — they corroborate early-print stability but are not a live variance measure.

**Fundamental ambiguity:** the MFM **cannot** distinguish a wrong e-steps from a wrong `L` (sensitivity) — both are the same measurement (commanded-mm vs measured-revs×L mismatch), and both look like genuine constant under-/over-extrusion. Therefore **never silently auto-compensate** (e.g. pulling `L` to `calibrated.mmPerRev`): that masks a real e-steps fault and prints dimensionally wrong parts while the MFM reports 100 %. Detect → **warn the operator** to recalibrate; only re-center adaptively (to save an in-progress print) alongside a persistent warning.

**`avgPercentage` is a whole-print integral, restarts only on pause/stop.** The toolboard's `totalExtrusionCommanded`/`totalMovementMeasured` are only ever `+=` in `CheckFilament`; they restart when the monitor goes `idle` via `Clear()`→`Reset()` (= not printing, i.e. pause/stop), never mid-print, and `M92` does not touch the monitor. So after an e-steps correction `avgPercentage` does **not** return to 100 % within the same print (historical biased extrusion stays in the mean) — do not use it as a success criterion. The per-segment `lastPercentage` (the actual P=4/P=5 trigger) normalises right after the correction; that's what matters.

**Only an e-steps change fixes the bias; `M221` does not.** The MFM derives `commandedMm` from e-steps (`steps / e-steps`), so the extrude-factor `M221` scales the issued steps → both physical feed *and* the MFM's `commandedMm` move together → ratio `measured/commanded` is unchanged. `M221` cures the under/over-extrusion but **not** the inevitable MFM error. Only changing e-steps (`M92`) shifts the ratio toward 100 %. But `M92` blocks (standstill lock), so it **cannot** run in `daemon.g` (see the daemon.g rule) — applying a correction must happen in a context allowed to block (operator recalibration, or a pause/trigger macro), never the background loop.

**Implemented flow-bias detector — split: DETECT in `filament/mfm-flow-bias.g`, APPLY in `filament-error.g`.** Detection (called by `trigger8.g` every 60 s while printing, non-blocking; it moved out of `daemon.g` on 2026-09-24) is a **time-sustained, settled drift — not a fixed distance** (a distance trigger reliably lands in an awkward section, e.g. many short moves the MFM reads poorly; the whole-print integral is instead intrinsically robust to momentary sections). Sampling every 60 s: inside the ±3 % deadband the window clears; outside it a settle window opens, and any move >3 % from the window reference restarts it (filters a *progressing* fault — a developing clog should pause, not be compensated). Only when avg stays outside the deadband **and** flat for the full 600 s window does it compute the bounded target `clamp(stepsPerMm*100/avgPercentage, ±5 %)` into `global.mfm_esteps_suggested`, set `mfm_esteps_detected`, and emit a non-blocking `M118` warning. **Application is deferred to `filament-error.g`** (a trigger/macro context that may block). The `M92` runs at the **very top, before all other checks**, on the *first* MFM error while a suggestion is pending and unapplied (`mfm_esteps_baseline == 0` guard). It must be here — **not** after the pause — because a resume reloads e-steps from the filament config and would wipe a later `M92`; applying on the first error (typically still one of the tolerated errors, which do not pause/resume) makes the correction stick and can resolve the bias before it escalates to a hard pause. `M92` blocks (`LockAllMovementSystemsAndWaitForStandstill`) → it stalls this trigger until the move queue drains, which is harmless because `filament-error.g` runs **out of band** (it is not the safety loop — that is exactly why the same `M92` is fatal in `daemon.g`, and why the detector must not apply it either: it runs on the Trigger channel, and a blocking command there holds up `trigger4.g`'s door downgrade). **`resume.g` re-asserts it**: resuming re-selects the tool, which reloads e-steps from the filament config and wipes the correction, so `resume.g` re-applies `M92 E{suggested}` after the reload (idempotent — `suggested` is the fixed clamped target). `print/finish.g` restores `M92 E{baseline}` (no cross-print leak; each print re-detects) — **before** the `M400`/`G4 S1` settle, never after: M92's endpoint rescale perturbs the reported extruder position by a rounding epsilon the daemon reads as motion, which combined with the flag clear at the end of `print/finish.g` fires the unsafe-state M112 (see "The mode-downgrade window", happened 2026-08-22). The earlier revision that applied `M92` *from the daemon* caused an emergency stop — never reintroduce that.

**The auto-recovery runs inside `pause.g`, never after the pause has committed.** RRF's only guard against a resume is the pause state: `M24` is ignored while "pausing"/"resuming" and accepted the moment the state is "paused", on every channel, and DWC greys out resume/jog/extrude only while "pausing". "Paused" is therefore an operator-open state — anything automatic that moves or extrudes during a pause must run *before* the pause commits, i.e. from within `pause.g`. `filament-error.g` arms `global.mfm_recovery_requested` right before its `M25`; `pause.g` consumes it after park + snapshot, runs `T R1 P0` → `filament/mfm-recovery.g` → `T-1 P0` and hands the verdict back in `global.mfm_recovery_result` (-1 = never ran). The earlier layout (recovery started by `filament-error.g` after `M25` returned) let an operator `M24` on HTTP interleave with the recovery on Autopause on 2026-09-03: `resume.g` pulled the head from X min onto the part while the recovery's 25 mm purge and nozzle clean ran there — blob, then a Y-driver position-tolerance collision. Commands on different channels are individually correct and simply interleave in the shared move queue; per-channel modes (`G90`/`M83`) are not the issue.

**Reduced speed depresses the MFM reading, so the MFM path never lowers the speed.** At a lower print speed the rotary sensor reads *lower*, not higher: stiction and quantisation at the wheel, and a larger relative ooze/PA share at low speed. The former `M220` backoff on P=4/P=5 (60/40/20 %) therefore made the errors worse. Its reading-gated restore deadlocked, and the time-based restore that broke the deadlock (T6) existed only because of it. Both were removed on 2026-09-24.

`filament-error.g` now tolerates the first 3 P=4/P=5 errors within 30 mm of extrusion by counting them in `mfm_error_count`. An error 30 s or more after the previous one starts a fresh count, checked when the error arrives, so no trigger is needed. The next error pauses the print hard, and the auto-recovery decides.

The flow-bias detector samples only at full speed: `move.speedFactor < 1` clears its drift window.

The heater-PWM fast-fail was removed as well. It checked `avgPwm < 0.15` and skipped the recovery when the value was low. On 2026-09-21 it confirmed two false positives. `avgPwm` is a 5 s average from the toolboard (`HeatPwmAverageTime`), and it drops whenever the heater gets less power, not only when no filament flows.

### Auto-Generated Files in Filament Directories
Calibration macros generate config files in filament directories, and `config.g`, `load.g` and `unload.g` are machine-generated by `filament-profile/regenerate.g`. None of these should be hand-edited — per-material customizations belong in `config-override.g` (parameters), `nozzle-<key>.g` (nozzle-specific parameters) and `temps.g` (temperatures).

A calibration result only ever describes the filament diameter and nozzle it was measured with, so `calibration/e-steps`, `calibration/nle` and `calibration/pressure-advance` write `config-auto-esteps-<key>.g`, `config-auto-nle-<key>.g` and `config-auto-pa-<key>.g` (`<key>` = `filament-profile/calibration-key.g`, e.g. `2.85-0.40`). `tpost0.g` loads them through `filament-profile/find-calibration-file.g`, whose fallback chain still picks up the nozzle-only files of the 2.85 mm era (on a 2.85 mm tool only) and the unsuffixed files predating the split; `filament/load-procedure.g` (is an NLE calibration present?), `filament-profile/apply-nozzle-file.g`, `filament-profile/create-nozzle-file.g` and `create-filament-profile` resolve through the same helper.
